# Known limits in 0.2.0-alpha.1

This list is part of the product contract. A useful diagnostic must distinguish evidence from assumptions.

## Source scanning

One initial UTF-8 BOM is consumed in memory before Babel parsing, so a following
shebang is at the start of the program and first-line diagnostic columns match
the same source without its encoding signature. Additional/noninitial U+FEFF
characters remain in the parser input, including those in strings or comments.
Scanning never rewrites source files.

Sources are parsed with `@babel/parser` (TypeScript for `.ts`/`.mts`/`.cts`, TypeScript+JSX for `.tsx`, JSX for JavaScript files, plus `decorators-legacy` and `explicitResourceManagement`) and environment reads are resolved with `@babel/traverse` scope analysis. This is not a compiler, type checker or general data-flow analyzer. Comments, strings, regex literals and JSX text are never treated as reads; template literal interpolations and JSX expressions are. String escapes in property names are decoded by the parser. Direct property reads, quoted keys, `'KEY' in process.env` checks, simple and nested `{ env: { KEY } } = process` destructuring, `globalThis.process`, `process`/`env` imported or required from `process`/`node:process` (including two-hop `import process from 'node:process'; const { env } = process;`), and referenced file-local `const env = process.env` / `const env = import.meta.env` aliases are supported. TypeScript wrappers such as `!`, `as`, and `satisfies` do not hide reads, writes or fallback defaults.

Computed keys, passing or spreading the entire environment object, unreferenced aliases of the whole environment object, re-exporting `env`/`process` across module boundaries (`export const env = process.env`, `export { env } from 'node:process'`), rest destructuring and computed defaults produce warnings. Only a complete recognized literal default makes a read optional; a literal used in a condition (`KEY || true ? a : b`) or as a prefix of a longer expression does not. Whether a default is semantically suitable still requires review. A locally bound `process` (parameter, declaration, catch binding) makes reads *through that binding* unknown with `SOURCE_SCOPE_UNRESOLVED`; global reads elsewhere in the same file are still reported. Files the parser cannot read report `SOURCE_UNREADABLE`; files it can only read with error recovery report `SOURCE_UNSUPPORTED`, and neither counts as complete.

Bounded support is included for **T3 Env** (`createEnv` imported or required via ESM/CommonJS from `@t3-oss/env-nextjs` or `@t3-oss/env-core`, verified through module bindings rather than function or library name heuristics) when `server`, `client` or `shared` schemas use static **Zod** validator chains (`z` imported or required from `zod`, `zod/v3`, `zod/v4`, or `zod/v4-mini`, sharing field-chain classification with standalone Zod while additionally allowing `z.coerce.*`). `runtimeEnv`, `runtimeEnvStrict`, `experimental__runtimeEnv` (including `runtimeEnv: import.meta.env` and static name mappings such as `{ apiUrl: process.env.ACTUAL_API_URL }` without inventing schema-key variable names) and `skipValidation` are respected. Non-empty `extends: [preset()]`, `createFinalSchema`, conditional/non-static schema validators, custom callbacks (`.refine()`, `.superRefine()`, `.transform()`), `.nonoptional()`, non-environment or missing `runtimeEnv` entries, spreads, escaped/unsupported T3 Env bindings, and computed `.default(...)` expressions mark the scan incomplete (`SOURCE_UNSUPPORTED`).

Bounded **Envalid** support recognizes `cleanEnv` and built-in `str`, `bool`, `num`, `email`, `host`, `port`, `url`, and `json` validators through runtime imports or unshadowed `require('envalid')` bindings (including renamed imports and CommonJS destructuring). Input must be a recognized Node environment object or supported file-local alias, and the schema and validator options must be inline static objects. Static `default` output values make a variable optional, including empty strings, null, undefined, and static JSON arrays/objects. Defaults are never executed, copied into reports or checked for credential validity. Metadata options `desc`, `example`, `docs`, and `choices` are accepted; this does not validate the choices or infer types.

`devDefault` and `testDefault` are conditional, so they do not make a variable universally optional: the scan is incomplete and the variable remains conservatively required. The same applies to custom validators, computed defaults, `requiredWhen`, unknown/duplicate options, and spread options. Dynamic schema entries, custom cleanEnv options/reporters, and unsupported inputs also produce `SOURCE_UNSUPPORTED`. Relative package imports such as the pinned upstream example's `require('../')` cannot be identified as Envalid by single-file analysis and remain unresolved. See the [Envalid API](https://github.com/af/envalid#api) for the underlying runtime behavior.

Bounded **standalone Zod** support recognizes object schemas parsed with `.parse`, `.safeParse`, `.parseAsync`, or `.safeParseAsync` against a supported Node/Vite environment object. It verifies runtime package bindings from `zod`, `zod/v3`, or `zod/v4` (ESM and CommonJS). Inline schemas and file-local schema aliases are supported; aliases must only be used for parsing, other bounded aliases or type queries. Reassigned, mutated, exported or escaped schemas remain unresolved. Direct namespace writes or passing the namespace itself elsewhere also prevent inference. The object shape must be an inline literal. See [Zod coverage](zod.md) for supported field chains and examples.

Static field chains can establish names and requiredness, but do not create executable Zod validation rules in EnvCheck. Custom transforms/refinements, coercion, conditional validators, computed/unusable defaults, unions, and unknown methods mark known fields conservatively required and analysis incomplete, except for a bounded outer-wrapper presence proof. A supported required base followed by recognized callback methods or bounded `pipe` calls and then an outer zero-argument `optional()`/`nullish()` can establish optional presence while retaining `SOURCE_UNSUPPORTED` and `complete:false`. Pipe is never a fully supported presence-preserving check. Its target must be one inline schema using verified Zod bindings and bounded syntax (supported bases, `url`, recursive `array`, static checks, optional/nullish); aliases, factories, callbacks/nested pipes in targets, unknown methods, computed arguments and the new method-chain inference for Mini remain outside this subset. See [Zod coverage](zod.md) for the exact boundary.

An optional/default/catch before opaque work can cause missing input to reach that work; another outer optional does not establish success. Zod 4 can run an already-optional inner input, unlike Zod 3's unconditional optional short circuit. Later callbacks or `.nonoptional()` invalidate earlier optionality; nullable alone does not admit undefined. Defaults/catches across opaque callbacks or pipes stay conservative, including some safe cases. This also narrows earlier overbroad callback-only inference such as `.optional().refine(fn).optional()`. The proof uses official v3.23.8/v4.3.5 sources, not execution of Zod or an inferred installed dependency version; motivating fixtures declare ranges. Dynamic, computed or duplicate shape entries also make analysis incomplete; known fields then remain conservatively required because their validators may be overridden. Independent direct reads, including T3 callback/option reads, keep their own requirements; only confirmed runtime mapping nodes receive schema optionality (the existing skipValidation flag handling remains separate).

Static mapped inputs such as `schema.parse({ endpoint: process.env.API_URL })` link the schema field to the actual environment name and read location. Inline maps and file-local `const` aliases consumed only by one parse call are supported. Each linked value must be a direct supported Node/Vite environment read, optionally wrapped in TypeScript syntax. Mutations, escapes, exports, multiple consumers, spreads, computed/duplicate keys and getters prevent schema optionality from overriding the direct reads. Unsupported or missing mapped schema fields remain incomplete. Object composition (`extend`, `partial`, `merge`), custom parse options and imported schemas remain unsupported. No callbacks, imports or application code are executed; credential validity and validation-result handling are not established.

Interprocedural defaults, values passed or re-exported across files, and other configuration wrappers (`config.get('KEY')`, convict, NestJS `ConfigService`) are not understood. EnvCheck never assumes that the mere presence of a library or a function named `createEnv`, `cleanEnv` or `parse` defines environment variables. Use explicit rules to document such requirements.

Inferred `required:true` for an independent raw read is a conservative source
contract, not proof that the application needs an explicit value. For example,
comparing an absent NODE_ENV to a string need not throw; this scanner does not
evaluate that application's branches or runtime defaults. The historical
benchmark retains NODE_ENV:false and openly records the resulting 49/7 score.

`NODE_ENV` and `NODE_OPTIONS` are ignored as Node built-ins for implicit source reads and unreferenced example checks; explicitly configuring them in `variables` or `when.variable` includes them in the local file contract. Vite's `MODE`, `BASE_URL`, `PROD`, `DEV` and `SSR` are ignored only for `import.meta.env`. Public variable prefixes do not establish that a secret is safe to expose. This version does not scan bundles for leaked credentials.

Declaration files and common generated/dependency directories are excluded. Directory scans also skip dot-prefixed children and symlinks. No tests are executed from scanned applications. Test sources included in the selected paths can contribute requirements; choose narrow source directories or files.

## Environment files

UTF-8 `envcheck.config.json`, example/local dotenv files, Compose YAML/JSON and
Compose env_file inputs accept one leading BOM (U+FEFF) in memory. Reads do not
rewrite files. U+FEFF within values is retained; no global replacement or trim
is used to remove BOMs. Repeated BOMs or BOMs after whitespace/newlines are not
normalized as encoding signatures. Line/column provenance treats the initial
signature as encoding, not a visible column; duplicates keep their original
line numbers. Repairs preserve an existing leading BOM and LF/CRLF without
adding another signature. Config version validation is independent of encoding.

Value parsing uses Node's `util.parseEnv`, not Docker's or a particular framework's loader. Some malformed dotenv lines may be tolerated by Node. Declaration/duplicate locations use bounded single-line keys and quoted multiline values, and are confirmed against names accepted by Node. Key capture offsets are used directly, including names such as `port` after `export` or names with hyphens/noninitial U+FEFF. When Node accepts a form the location matcher cannot establish (for example, a carriage return inside a key), provenance contains only `file`, without invented line/column; text output says `position unknown`. No variable expansion is performed. File precedence is a configured local model, with later files winning; it does not include the host environment.

An empty example value is a documentation placeholder and is not itself an error. A nonempty placeholder can satisfy a local presence check, so a successful check does not establish credential validity. Do not use fake credentials to make a real integration appear verified.

## Docker Compose

The YAML library can silently consume stream BOM tokens after blank lines or
comments, as well as a second initial BOM after our one-signature decoding step.
EnvCheck rejects those extra stream markers: scan reports `COMPOSE_UNSUPPORTED`
with incomplete/unknown coverage and the marker location. Both repair preview
and apply refuse with an encoding diagnosis, even when there are no known
additions; the original bytes remain unchanged. Detection uses the public YAML
CST parser, not a global U+FEFF replacement. U+FEFF belonging to scalar values
(plain, quoted or block) or comments is retained, with LF/CRLF and one existing
leading signature preserved through supported repairs.
Before writing inputs containing U+FEFF, EnvCheck also compares the intended
edited YAML data with a re-read of the serialized output. It refuses if a data
character would become a stream signature or any other data would change;
comments and scalar contents are never globally stripped or counted as BOMs.

Select exactly one service matching the selected app sources. Compose files are parsed with the `yaml` package as a single YAML 1.2 document; JSON is accepted as YAML. Anchors, aliases and `<<` merge keys are resolved, with explicit keys overriding merged ones. Parser errors, duplicate keys, parser warnings (including Compose-specific tags such as `!reset` and `!override`), multiple documents, interpolated `env_file` paths, custom `env_file` formats other than `"raw"`, `include`/`extends` and multi-file overlays generate incomplete coverage. Parser diagnostics are not copied into reports because they can quote values.

The scanner recognizes service `environment` declarations and keys in literal short `env_file` paths as well as long `{ path, required, format: "raw" }` objects. When `required: false` is set on an `env_file` entry and that file does not exist locally, it is skipped without a missing-file error, preserving earlier `env_file` declarations while reporting any required variable not declared elsewhere as `COMPOSE_VARIABLE_MISSING`. Later unsupported, unreadable, or missing `required: true` `env_file` entries make service coverage incomplete (`unknown`) and invalidate earlier `env_file` declarations so stale values or empty flags are not retained, while allowing subsequent valid `env_file` or `service.environment` declarations to take precedence. Later `env_file` entries override earlier files; `environment` overrides all `env_file` declarations. Invalid or unsupported `service.environment` entries invalidate only the affected variable key when identifiable (or all `env_file` declarations when `service.environment` itself is a non-map/non-list structure). Plain interpolation and host pass-through count as declarations, even if the external value is missing. It does not evaluate `${...}`, profile activation, image `ENV`, Docker secrets, build args or the actual container environment. It does not infer how a frontend build receives variables. Build-time frontend variables should not be treated as runtime server variables; choose an appropriate source scope.

For `env_file` with `format: "raw"`, a bounded single-line `NAME=value` reader preserves literal quotes, `#`, `$` and value whitespace when deciding whether the declaration is empty; a BOM and CRLF are supported. This follows the [Compose raw-format contract](https://docs.docker.com/reference/compose-file/services/#format) and [Docker CLI kvfile semantics](https://pkg.go.dev/github.com/Docker/CLI/pkg/kvfile); it does not perform interpolation or dotenv unquoting. Bare host-only names, multiline values and other unsupported raw syntax make coverage incomplete. A later unsupported bare name invalidates an earlier declaration of that name rather than retaining stale certainty; an explicit service environment declaration still overrides it. No host environment is consulted.

Compose fixtures demonstrate declaration checks and are not full runnable apps. Running a fixture with Docker is not a validation step for this release.

A missing or unreadable service env_file keeps service declarations unknown. A structurally repaired target may still have incomplete comparison coverage. Environment-scan completeness does not establish absence of credentials embedded in source; the tool does not detect such credentials.

## Agents and repairs

The portable skill is an instruction package around the CLI. It cannot guarantee that an agent invokes it or follows it correctly. Installation and format are tested, but actual Codex/Claude behavioral evaluations remain future work. The skill does not create credentials, manage accounts or deploy. A report omits setting values; other agent actions may still read project files, subject to the agent's permissions and provider policies.

`fix-example` applies only placeholder additions to an explicitly configured file ending in `.example`, `.sample` or `.template`. `fix-compose` adds only `${VAR:?Set VAR locally}` interpolation references to the selected service's `environment` in a `.yaml`, `.yml` or `.json` Compose file. It preserves comments (including an explicitly null `environment`) and line endings, and refuses `include`/`extends`, unsupported existing `environment` structures or entries, aliased or merge-inherited targets, environment mappings containing merge keys, and shared YAML anchors on the edited root/services/service/environment path (returning `INPUT_ERROR`, exit `2`, in both preview and `--apply`, even when there are no additions, while general scan warnings such as unresolved source expressions or `env_file` warnings do not block editing `service.environment`). Editing a shared anchor could otherwise change other services. Unshared anchors and unrelated aliases may be preserved. Both commands use a same-directory replacement for an existing file after checking for intervening changes. This is not a cross-process locking protocol: concurrent editors should not write the same file during repair. Applying a documentation or Compose wiring repair does not supply real credentials or make an integration work at runtime.

## Comparison

`scope.comparable` records whether normalized source selections, ignored variables and the selected Compose file/service match across snapshots. This conservatively compares declared selections; it does not prove that different, overlapping source selections are semantically equivalent. A change in these selections makes the comparison incomplete even when both scans are individually complete; removals and resolved findings may then reflect scope changes. `--strict` fails on incomplete comparison coverage, including an incomplete older snapshot with a clean target. Default comparison policy still fails on current errors, even with no diff.

Finding matching counts variable-level project findings (`UNDOCUMENTED_VARIABLE`, `COMPOSE_VARIABLE_MISSING`, `CONDITION_UNRESOLVED`, `COMPOSE_VALUE_EMPTY`, `REQUIRED_VALUE_MISSING`) by rule, severity and variable (ignoring first-location file shifts when reads are added in another file or a file is renamed), while occurrence-level findings (such as `UNRESOLVED_ENV_ACCESS`, `DUPLICATE_ENV_DECLARATION`, `INVALID_VARIABLE_VALUE`, and `UNREFERENCED_EXAMPLE_VARIABLE`) match by rule, severity, variable and first location file, ignoring line shifts. This detects added/removed unknown occurrences without treating inserted comments as new problems; replacing one unresolved expression with another with the same identity and count is not classified as a semantic change. Markdown output sanitizes application paths and does not label an incomplete comparison clean.

`compare` accepts either two directories or `--base REF` with an optional `--head REF`. Git mode invokes read-only local plumbing commands, does not checkout or fetch, and removes its temporary snapshot afterwards. It reads only selected tracked source/configuration inputs for committed snapshots. A working-tree target includes untracked source files. Symlinked selected Git inputs, submodules and nonportable paths are rejected. Large inputs are bounded: 8 MiB per file, 32 MiB total, 10,000 materialized files, bounded tree output and per-command timeouts.

Scopes are taken independently from both configurations; users must choose comparable snapshots. App directories that did not exist in the older revision can have incomplete source coverage. Type rules and conditional policies are explicit; arbitrary code changes and semantic changes to fallback literals are not classified. Conditional expected values are compared in memory, never included in reports. An unchanged error in the new snapshot still makes the command fail. Git must be installed; refs must already be available locally. Failure to read a Git input is an operational error, not an empty comparison.
